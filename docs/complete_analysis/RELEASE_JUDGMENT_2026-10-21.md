## 5. 運営者が決める項目

### 5-1. 規約・特商法・プライバシー
下書き（`docs/drafts/`）は、公開ページへ未反映。次を決めてから公開する。
- 特商法の表示：屋号＋氏名・住所・電話は請求があれば開示（運営者の選択B）。この運用でよいか最終確認。
- 公開日（2026-10-20）と、規約の改定の通知方法。
- 返金：今回は実装対象外。規約に「デジタルコンテンツの性質上、提供後の返品・返金は受け付けない」と、運営者が個別に判断する旨をどう書くか。
- 問い合わせ先（メール）の表記。
- 個人情報の保管期間と、委託先（Supabase・Vercel・Stripe・Google・X）の記載。

### 5-2. アカウント削除の手順（提案）
購入の記録がある利用者は、DB の参照制約で、いまの手順（ユーザーの削除）では消せない。次の手順を、SQL Editor 専用の関数にする案。
1. 本人確認（登録メール・ログイン方法）。
2. その人の登録（`account_report_registrations`）を削除する。
3. その人の記録の回答・結果・MIRROR を削除するか匿名化する。
4. 購入の記録（注文・支払い）は会計のために残し、ユーザーとの紐付けだけを外す。
5. 保存済みの完全解析のファイルを Storage から削除し、納品を停止する（固有リンクは使えなくなる）。
6. 最後に認証ユーザーを削除する。
7. 実行の記録（誰の・いつ）を監査ログに残す。
これは新しい DB 関数と試験が必要。ご承認いただければ作る。

### 5-3. 推奨判断
| 項目 | 推奨 | 理由 |
| --- | --- | --- |
| GA4 の拡張計測「ブラウザの履歴に基づくページの変更」 | **無効にする** | アドレスを書き換えるページ（`/report-link`）で、`#` の秘密値が計測に送られないようにするため。管理画面の設定のみ。 |
| 購入の作りすぎの対策 | まず**今のまま**（記録ごとに1時間20件）で公開し、Vercel のレート制限（接続元ごと）を検討 | DB の変更なしで入れられる。プランで使えるかは要確認。 |
| report_sample の noindex | 運営者の判断（検索に出すか）。**既定は noindex を推奨** | 完全解析のサンプルと扱いをそろえる。サンプルは別のページから案内しているので、検索に出さなくても導線は残る。 |
| 固有リンクの再発行 | **通常は行わない**運用 | 再発行すると請求書のリンクも使えなくなる。漏れの疑いがあるときだけ行い、購入者へ新しいリンクを連絡する手順を決めておく。 |

## 6. 運用で注意すること
- Webhook は、販売を止めている間も有効のままにする（支払い済みの納品を落とさないため）。
- 決済画面の期限は35分。
- 悪用で停止した納品は、再発行しない（再発行すると有効に戻る）。
- 毎日、DB の `stripe_webhook_events` の失敗・`complete_reports` の失敗・1時間以上の決済待ちを SQL で確かめる（ランタイムログは1時間しか残らない）。

## 8. 本番公開から販売開始までの安全な順番
1. 本番 DB の完全バックアップ。Vercel の環境変数の控え。ロールバック手順の確認。
2. 本番用の SQL を作成し、レビュー。運営者が SQL Editor で適用し、読み取りで確認。
3. Production の環境変数を設定（`COMPLETE_SALES_OPEN` は設定しない＝販売停止のまま）。Stripe（live）の Webhook・価格・メールを設定。
4. 規約・特商法・プライバシーを公開（承認後）。同意の版・DB の確認・特商法リンクを同時に反映。
5. main へ反映し、Production を**販売を閉じたまま**デプロイ。READY を確認。
6. 公開ページの確認（リンク切れ・OGP 画像すべて 200・SNS のキャッシュ更新・GA4 の DebugView）。
7. GA4 の拡張計測の設定変更。
8. 販売を開く（`COMPLETE_SALES_OPEN=true`）。運営者が少額の実購入を1件行い、A と B の購入→請求書のリンク→登録→マイページ表示を確認。必要なら Stripe 管理画面で返金（返金は納品が止まる）。
9. 問題があれば、`COMPLETE_SALES_OPEN` を外して販売を閉じる（Webhook は有効のまま）。
10. 告知。
