## 1. レポートの意味上の境界（最優先）

共鳴診断は100問版のETIで用いる20軸座標・MIRROR比較を**再利用する簡易な象徴モデル**である。3回答で本人の20特性を実測したわけではない。

画面とレポートには次の一文を共通して配置する（詳細側のグラフ冒頭、本文は短縮可）：

> この図は、選んだ元素・武器種・国家の代表モデルと、キャラクターの登録モデルを比べたものです。性格検査の得点や、実際の一致率ではありません。

- 禁止：ユーザーのBig Five「実測値」、性格の確定診断、心理的な因果の断言、医学的表現、「キャラが最も似ている」「一致率XX%」、同一人物への強制的な人格評価。
- 許容：**モデルの座標・方向・相違**を無目盛り図で示す、代表値の違いを根拠とした説明、あくまで仮説としての共鳴解釈。
- 66名の均等化固定割当のため、排出キャラは純粋なMIRROR順位1位とは限らない。**排出された理由は「選択した人物像と共鳴し得る候補として割り当てた」**とし、統計的最良の相手と宣言しない。
- レポート本文は、結果と無関係なAI即興生成ではなく、**固定辞書＋再現可能な文章合成**を基本とする。公開後のモデル変更で過去購入文が変わらないよう保存する。

## 2. 計算データ：3回答 → 20軸

既存正本 `js/eti_v2_prototypes.js`（受領時Step0抽出と照合）から以下を取得する。

- 回答 Q1＝元素 `e` → `U_P[a] = ELEMENT_PROTOTYPES_V2.values[e][a]`、軸 `a∈{O,C,E,A,N}`。
- 回答 Q2＝武器 `w` → `U_S[a] = WEAPON_PROTOTYPES_V2.values[w][a]`、軸 `a∈{AGY,REL,ROL,REF,AUT}`。
- 回答 Q3＝国家 `n` → `U_V[a] = NATION_PROTOTYPES_V2.values[n][a]`、軸 `a∈{SD,ST,HE,AC,PO,SE,CO,TR,BE,UN}`。
- MIRRORの登録座標：`C_P, C_S, C_V = characters118_v2_1[mirror_character]`。登録データの版は `ETI-CHAR-2.1.0`、各値0〜100。
- `n=ナドクライ` を内部キーに、表示だけ `ナド・クライ` とする。
- **注意**：元素本人側のPERSONALITYは同じ元素なら完全に同じ。武器本人側STYLE・国家本人側VALUESも同様。これは仕様であり、「個人の20軸を推定できた」とは表現しない。
- 取得した20軸の生値はサーバー内部のスナップショットには含めてもよいが、無目盛り比較図以外で本人の数値スコアを画面に表示しない。

## 3. 図の数式・表示規則

### 3-1. PERSONA（5軸レーダー）

- 比較データ：`U_P[a]` と `C_P[a]` （両方0〜100の共通座標）。
- 各半径 `r_U[a]=U_P[a]/100`、`r_C[a]=C_P[a]/100`。5軸の角度は、正本配列順 `[O,C,E,A,N]` とし、始点-90°、72°刻み。表示する軸は「開放性、誠実性、外向性、協調性、感受性」。
- 目盛り線・0〜100など数字・面積をスコアとして強調する文言は表示しない。色はアナタ＝青、MIRROR＝金（既存見本の色）。
- 下部注釈は「元素の代表モデル／人物登録モデルを比較」。
- 比較式：`dP=sqrt((Σ_a ((U_P[a]-C_P[a])/100)^2)/5)`。**内部だけ**に使用する。

### 3-2. STYLE（5軸ペア横棒）

- 比較データ `U_S[a]` と `C_S[a]`、軸順 `[AGY,REL,ROL,REF,AUT]`。幅はそれぞれ `value/100`。
- 表示項目：「主導性、関係調整、役割持続、媒介思考、自律距離」。文字と2本の色棒を並べる。数値ラベルなし、ツールチップで数字を露出しない。
- 内部距離 `dS=sqrt((Σ_a ((U_S[a]-C_S[a])/100)^2)/5)`。

### 3-3. VALUES（10価値観・円形レーダーまたは円環の10点）

- 比較対象：`U_V[a]` と `C_V[a]`、軸順 `[SD,ST,HE,AC,PO,SE,CO,TR,BE,UN]`。描画半径は値÷100、始点-90°、36°刻み。
- 表示ラベル：「自分で選ぶ、新しい刺激、楽しみ、達成、影響力、安定、節度、伝統、思いやり、公正さ」。スマホ幅で長ければ外周10ラベルを隠し、図の下に2列の凡例。数値表示なし。
- **価値観のMIRROR内部類似性は本家と同じ平均中心化コサイン**：
  - `center(x)=x-mean(x)`、`cos(x,y)=dot(center(x),center(y))/(norm(center(x))*norm(center(y)))`。
  - いずれかが零ベクトルなら cos=0（本家がvSim=0.5にする場合と同じ）。
  - `vSim=(cos+1)/2`。**数値は非表示**。
- 注意：原図の値をそのまま描画しても構わないが、価値観の「共鳴」文章は**値の大きさの単純一致ではなく、平均中心化した相対的な優先度**を使う。

### 3-4. SYMBOLS（象徴的な近さ）

- **元素**：本人の選択元素代表 `U_P` と7元素代表 `E_i` の `d_i = sqrt(mean(((U_P[a]-E_i[a])/100)^2))` を計算。表示用に `closeness_i=1-d_i` として正規化せず、あくまで内部並べ替えに使う。
- 見せる場合は7元素を距離の近い順に並べ、**棒長は `1-d_i` の相対描画**。最初の選択元素が必ず距離0で最大となる、情報論的に既知の結果であることを注記する。
- **武器種と国家も図示するなら**、武器 `U_S` と各武器代表は5軸RMSE、国家 `U_V` と各国家代表は**本家と同じ平均中心化コサイン**の距離 `(1-cos)/2` を使う。領域間の棒長を横断比較してはいけない。
- 重要：それらは選択済みカテゴリの代表座標から導かれた**「他の分類との象徴的な位置関係」**であり、3問で他の7/5/8カテゴリへの適性を測定した結果ではない。
- 商品の主役がキャラ名のため、初期版のSYMBOLSは**元素7本の簡素な図＋武器・国家は文章**で十分。3グラフを必須にしない。ユーザーの負荷と誤認リスクを減らす。

### 3-5. 共鳴する／異なる領域の選び方

- `pSim=1-dP`, `sSim=1-dS`, `vSim=(cos(center(U_V),center(C_V))+1)/2`。
- 本家MIRRORの総合参照値 `M=0.40*pSim+0.30*sSim+0.30*vSim` は**内部の照合用**。自動割当済みのキャラを変更しない・表示しない。
- 結果説明に使う領域は、**最大の `pSim,sSim,vSim` の領域を「モデル上、比較的近い側面」**、最小の領域を「違いが表れた側面」とする。ただし差 `max-min < 0.05` なら強弱を断定せず「3領域で大きな偏りはありません」と記載。
- `vSim` と `pSim/sSim` は数学的性質が異なるため、この大小比較は**物語編集用の暫定ルール**であり、心理学的な優劣判定ではない。まず全280ケースを監査して偏り・不自然さがないか確認する。問題があれば、領域の総合比較を廃止して**軸ごとの一致・差異の説明のみ**にする。
- 詳細に挙げる個別軸：P/Sは `abs(U-C)` が小さい軸1個・大きい軸1個。VALUESは `abs((U-mean(U))-(C-mean(C)))` が小さい軸1個・大きい軸1個。ただし差が数点以内などのほぼ同じ場合は誇張しない。
- 必ず「データ上は」「このモデルでは」「〜の可能性」という限定表現を使う。選択したカテゴリと人物像から本人の人生史・恋愛・病歴を作らない。

## 4. レポート本文6章・テンプレートと文章合成

本文の完成は**代表辞書に基づく決定的な組み立て**とする。同じ `e,w,n,mirror,templateVersion` から常に同じ文章を生成する。数値グラフの説明は図のデータに連動させる。以下の文言は正式本文の**土台**であり、元素7種・武器5種・国家8種・キャラ66名それぞれの個別辞書を、Claudeが推測で作成してはいけない。辞書は別途内容レビューを要する。

### PERSONA（180〜260字）
見出し：**アナタの人物像**。まず共鳴キャラ名を表示。
テンプレート：
> アナタの3つの選択は、〔元素の解釈：内面〕を大切にし、〔武器種の解釈：人との関わり方〕を選び、〔国家の解釈：価値観〕に心を向ける人物像を描きます。これはアナタのすべてを表すものではありませんが、いま惹かれる在り方を見つめる手掛かりになります。〔選択の組み合わせ固有の一文〕

- 元素・武器・国家の語彙は本家 `index.html` の正本と意味の整合をとる。文章はただ3文を機械接続しただけにならないよう接続辞書を使う。

### STYLE（120〜190字）
見出し：**行動の傾向の比較**。
> 〔選択した武器の象徴的な行動文〕。図は、その武器種の代表モデルと〔人物名〕の登録モデルを比較したものです。〔最も共通するSTYLE軸の名称＋意味を解説〕。一方、〔差が大きい軸の名称＋無理のない解説〕という違いも読み取れます。

- スコアや本人の能力評価に言い換えない。

### VALUES（120〜190字）
見出し：**価値観の地図**。
> 〔選択国家が象徴する優先価値の文〕。〔人物名〕のモデルにも〔平均中心化した相対優先度が近い価値観の名称〕という共通点が見られます。対して、〔相対優先度が異なる価値観の名称〕には違いがあり、同じ結果でも大切にするものの現れ方は一様ではありません。

- 価値観の実測、各国の人々の性格、公式キャラクター設定の事実とは混同しない。

### SYMBOLS（130〜200字）
見出し：**元素・武器・国家の象徴**。
> 今回の結果は〔元素〕×〔武器種〕×〔国家〕。〔元素は内面の象徴、武器は行動の象徴、国家は価値観の象徴として解説〕。下の元素図は〔選択した元素〕の代表座標と、ほかの元素モデルとの距離を示したものです。ほかの元素を個別に測定した結果ではありません。

### RESONANCE（260〜380字、商品の中心）
見出し：**なぜ、この人物が現れたのか**。
> アナタに共鳴する人物として現れたのは、〔人物名〕。この人物は、3つの選択が描く人物像と比較したとき、〔明確な共通軸の自然文〕で重なる部分があります。〔対象となる領域がどのような場面で現れるかを具体例に置き換えた文章〕。一方で、〔差が見られる軸の説明〕という違いもあります。共鳴とは、すべてが同じという意味ではありません。〔キャラを知る人が楽しめる、過剰な設定断定のない解釈文〕。

- **厳禁**：「このキャラになったのは、類似度が一番高いから」。均等排出調整により事実ではない場合がある。
- 人物の具体的な公式設定・セリフを勝手に引用しない。固有の性格解説は、社内登録の `basis_tags` と既存人物座標から、検証できる範囲で執筆する。
- 決定的な「共通点」1件と「異なる点」1件を毎回選ぶ。数値・順位は本文に出さない。

### JOURNEY（120〜200字）
見出し：**アナタ自身への問い**。
> 〔3選択に対応する問いの導入〕。アナタは、〔元素のテーマを生活に引き寄せた問い〕をどんな場面で感じますか。〔武器・国家を組み合わせた第二の問い〕。答えを急がず、自分の言葉で考えてみることが、今回の結果の使い方のひとつです。

- 行動指示や断言ではなく、内省の問いで閉じる。

### 構成の順序・販売見本
- 商品を売る際の先頭は「MIRRORの大きな名前＋PERSONA/RESONANCEの導入」。6章の並びは現行の PERSONA → STYLE → VALUES → SYMBOLS → RESONANCE → JOURNEY に合わせて実装してよいが、**購入直後はMIRRORとの共鳴の要旨を最初に見せる**。
- 無料見本のダミー図は現在の固定図を維持する。実データは購入後のみ（ただし個人測定値ではない）。全員同じ見本の注記は維持する。
- 文章は概ね900〜1,350字＋図とする。長文の繰り返しを避け、500円の買切り商品として読みやすさを優先。

## 5. 販売・スナップショット・再閲覧（実装方針）

### 5-1. 商品と販売条件
- `product_code`: `resonance_report_v1`（提案。既存商品コードと衝突しないこと）。税込500円、単発購入、定期購入なし、マイページ非連携。
- 販売スイッチは原則オフ。Preview/本番を別系統で保持し、Previewテストが本番に書き込まれないよう既存ガードに従う。Stripeの金額・通貨・Price/Product ID は**サーバー定数／環境変数側だけ**で確定し、リクエストから金額を受け取らない。
- DB SQLはまずDRAFTで出し、レビューとユーザー承認まで適用しない。

### 5-2. DBは既存の本家注文テーブルと分離
- `resonance_orders`: `id UUID PK`, `stripe_session_id UNIQUE`, `stripe_payment_intent_id UNIQUE nullable`, `amount_jpy INTEGER NOT NULL CHECK(amount_jpy=500)`, `currency='jpy'`, `status`（pending/paid/refunded等）, `created_at`, `paid_at`, `snapshot_id UNIQUE nullable`。
- `resonance_reports`: `id UUID PK`, `order_id UNIQUE FK`, `snapshot JSONB NOT NULL`, `rendered_html` または `rendered_payload JSONB NOT NULL`, `template_version`, `created_at`。生成済本文と図の座標を保存し、再閲覧時は必ず保存済を読む。
- `resonance_access_tokens`: `id`, `report_id`, `token_hash UNIQUE`, `revoked_at`, `created_at`, `last_used_at`（最小限。長期アクセス用は推測不能なランダム値を用いハッシュのみDB保存）。
- 状態は追加購入・再決済・払い戻し・途中失敗を考慮して冪等に更新。重複webhookでレポートが二重生成されないこと。
- 推奨：既存の本家の「#t=」方式を踏襲するなら、URL fragmentはサーバーに自動送信されないため、クライアントで一度取得しセキュアな交換APIに送ってhttpOnly Cookie等の短期セッションへ変換する。**URLやトークンをアクセスログ・GA4・外部シェアに記録しない**。

### 5-3. 購入完了フロー
1. 購入ボタンでサーバーが回答キーと固定割当を**サーバーで再検証**し、注文ドラフトを作成。
2. サーバー発行のStripe Checkoutに遷移。注文IDと検証済snapshotIDをmetadataに記録（回答全文や秘密トークンをmetadataへ載せない）。
3. **署名検証済みwebhook**で決済済みを確定し、金額JPY500、対象商品、環境、注文ID、支払い状態を再検証。
4. snapshot生成と本文レンダリングを一度だけ実施し、保存。権利トークンを払い出す。購入完了画面の戻りURLだけで決済確定しない。
5. receipt導線からレポートへ。再閲覧時は生成済みの`rendered_payload`を表示し、現在のエンジンを使って再計算しない。
6. 決済後の処理失敗に備え、webhookのリトライと復旧ジョブ（手動復旧手順でも可）を明確にする。画面で「購入済みだが準備中」の状態を表現できるようにする。
